## 4. 수치와 기존 기획의 충돌

기획의 현행 원칙은 “호감도는 참고”, 명시적 이해·교제 확인으로 진행, 친밀한 장면의 미룸·취향·공개 범위에 따른 점수 차이 없음이다. 따라서 예시 30/60/80/90을 그대로 기존 게이트로 넣지 않았다.

원래 award_once의 보상 합계를 정적으로 계산했다. 다음은 자기 소개 +10, C06/C07을 모두 해당 인물에 집중 +4, 앞선 선택 일상 모두 완료를 가정한 **이벤트 진입 전 상한**이다. 실제 전체 분기 플레이로 측정한 최댓값이나 보장 최솟값은 아니다.

| 인물 | R07 전 | R12 전 | R15 전 | R16 전 |
|---|---:|---:|---:|---:|
| 리아 | 51 | 67 | 79 | 86 |
| 지현 | 50 | 66 | 78 | 85 |
| 유진 | 50 | 66 | 78 | 85 |
| 서윤 | 50 | 66 | 78 | 85 |

따라서 첫 이벤트 60, 중반 특별 이벤트 80은 좋은 경로에서도 도달할 수 없다. 최종 R16 보상은 이후 +4이므로 그 이전에 90을 요구하는 것도 성립하지 않는다. 가중치를 먼저 바꾸고 다시 계산하지 않은 상태에서 적용하면 기존 콘텐츠를 막는다.

이번 모델은 `evaluate(..., proposal=True)`로 요청서 예시 수치를 진단할 수 있지만, 본편에서는 호출하지 않는다. 기본 호환 모드에서는 진행·교제·현재의 동의·필수 플래그만 별도 검토한다. **수치 통과는 CG 해금이 아니다.** 진엔딩은 대본·CG가 없으므로 판정 함수도 해금 가능으로 돌려주지 않는다.

기존 선택에는 호감도 보상을 그대로 적용한다. 새 `progression_apply(choice_id, who, affection_delta, relation_delta)`는 향후 승인된 선택 효과에 한해 두 수치를 독립 증감시키는 API다. 같은 선택 ID의 반복 실행으로 보상을 누적할 수 없다. 새 대사나 업무 선택 예문을 강제로 끼워 넣지 않았다.

## 5. 네 히로인 관계 설계

고유 수치는 기존 memory 증거에서 계산하고, 별도의 새 선택 보너스만 저장한다. 이를 통해 과거 저장에도 실제 남은 증거만 반영하며, 반복 메시지나 화면 열기로 수치를 벌지 않는다. 아래는 **첫 검토용 가중치**이며 사용자 확정/출시 밸런스라고 하지 않는다.

| 인물 | 실제 증거 / 변화 | R07 전 관계 예 | 후반 분기 보존 |
|---|---|---|---|
| 강리아 · 편안함 | 핵심 이해 +15, 휴식 응답 세 안 각각 +12, 연락 합의 +10, 지원 세 안 +12, 갈등에 솔직/질문 +8·덮어주기 -8, 실제 수습 +25, 미래 합의 +10, 장난 강도 세 안 +4 | 핵심 이해·휴식·연락이면 37 | 갈등 수습과 계속/종료 선택 유지. 한번 덮어준 경로도 수습 후 80 가능 |
| 백지현 · 존중 | 핵심 이해 +15, R03 응답 세 안 +10, 애정 범위 세 안 +15, 지원 세 안 +15, 갈등 응답 세 안 +10, 실제 역할 검증 +25, 미래 약속 +10 | 이해·응답·범위면 40 | 업무 책임과 사적 주도권 취향을 섞지 않음. 칭찬·M 성향을 업무 벌로 보상하지 않음 |
| 차유진 · 신뢰 | 핵심 이해 +15, R03 응답 +10, 표현 방식 +15, 지원 범위 지킴 +15·침범 -15, 범위 재합의 +10, 행동 검증 +25, 수습 완료 +15, 미래 표현 +10 | 이해·응답·표현이면 40 | 조용한 적극성과 독점욕 유지. 실수 뒤 실제 수습을 인정하며 감시·답장시간 벌점 없음 |

공통 정책:
- 첫 일반 연애 CG: 기존 해당 사건/실제 표시를 기준으로 한다. 아직 연결하지 않은 일반 CG는 해금하지 않는다.
- 첫 기본 친밀 이벤트: 기존 R07의 교제·명시적 진행 선택을 유지한다. 새 60/30 문턱은 붙이지 않는다.
- 특별 이벤트: 기존 R12/R15와 의상 선택을 유지한다. 새 80/70 문턱은 진단 자료만 제공한다.
- 진엔딩: 네 루트 모두 새 대본·CG·핵심 조건이 확정되지 않았다. 기존 결말을 진엔딩으로 이름만 바꾸지 않는다.
- 조건/마음이 맞지 않거나 미루면 기존 대화·귀가·다음 만남 경로를 유지한다. 수치 때문에 새 실패 장면을 만들지 않는다.
- 관계 변화는 새 상태 화면에서 단계/수치로 확인한다. 기존 대사는 변경하지 않았고, 수치별 새 반응 대사도 작성하지 않았다.
- 옵션으로 정확한 새 관계 수치를 숨길 수 있다. 기존 헤더의 호감도 숫자는 기존 화면을 보존한 상태다.

## 6. 저장·롤백·분기 재진입

- 회차 상태: progression_state, affinity, memory, completed, dating, active_route와 기존 모든 변수는 Ren’Py의 기본 저장 대상으로 둔다.
- 임의로 일부 변수만 JSON에 넣고 Jump하지 않는다. 사건/선택 직전의 **전체 네이티브 저장**으로 호출 스택과 진행 상태를 복원한다.
- 슬롯은 `flow-<고유ID>`, 지점당 최근 한 개다. 총 272개로 상한이 있으며 일반 수동 슬롯1~4와 구분한다. 재방문 시 같은 지점의 이전 회차 상태를 덮어쓸 수 있으므로 “분기별 무제한 보관”은 아니다.
- 방문·CG·결말 기록은 persistent에 분리한다. CG/결말 영구 기록은 과거 회차를 불러와도 소실되지 않도록 합집합으로 관리한다.
- 재진입은 FileLoad의 기본 확인·서명·알 수 없는 저장 경고를 유지한다. label로 강제 이동하지 않는다.
- 현재 빌드 표식과 저장이 모두 있어야 재진입 버튼이 활성화된다. 과거 버전에서 방문만 기록된 노드는 잠금/안내 상태로 표시한다.
- 이전 저장에 기본 필드를 추가하고 기존 memory에서 관계 증거를 읽는다. 알 수 없는 구버전 새 상태를 초기화할 경우에만 마이그레이션 후 롤백을 막는다. 실제 원본 옛 저장 파일은 읽지 않았다.
- 자동 기록은 설정에서 끌 수 있다. 디스크 저장 실패는 안내하고 이야기 진행을 계속한다.
- 네이티브 저장은 호출 문장 시작을 저장한다는 [Ren’Py 저장 문서](https://www.renpy.org/doc/html/save_load_rollback.html)를 따랐다. 실제 엔진에서 재진입/롤백을 검증하기 전 이 부분을 출시하지 않는다.

## 7. CG·회상·제작량

기존 event_cg_plan을 읽어 16개 의상별 이벤트 세트, 기본 본장면48·도입16·도입표정16 = 총80개 자산 항목을 가져온다. 요청서의 임시 36~40장으로 기존 계획을 축소하지 않는다. 일반 CG18 계획과 메시지 사진·Live2D는 이80개와 다른 제작 범주다.

화면의 수집률 분모는 실제 로드 가능한 등록 자산이다. 미제공 계획80개를 채워진 자산으로 취급하지 않으며 등록0이면 수집률도 미정으로 표시한다.

CG 기록은 event_cut 화면의 상호작용이 끝난 다음 수행한다. 조건이 맞거나 이벤트 페이지 목록을 만들었다는 이유로 해금하지 않는다. 실제 표시 ID/경로가 카탈로그와 일치하고 파일이 로드 가능해야 한다. 표정 이미지가 없어 기본 이미지로 대체되면 실제 기본 이미지에만 기록한다.

일반·연애·성인·엔딩 분류 UI를 준비했다. 현재 자동 카탈로그는 기존 도입/본장면만 연결하므로 일반/엔딩 탭에는 아직 자산이 없을 수 있다. 새 일반/엔딩 CG 제작·연결은 미완료다.

완료된 기존 이벤트는 [Ren’Py Replay](https://www.renpy.org/doc/html/rooms.html#replay)로 다시 연다. 회상 중에는 새 점수·CG·결말 영구 기록을 주지 않는다. 종료 후 원래 플레이로 돌아오는 엔진 동작은 런타임 검사 대상으로 남긴다.

## 8. 메신저·의상·Live2D

office_phone의 기존 연락처·대화 기록·입력 중·사진 확대·답장과 말투를 재사용한다. 중요 답장 직전에 재진입 지점을 추가했다. 기존 답장은 memory 기반이므로 관계 수치 재계산에 무제한 반복 보상이 없다.

회사 메신저는 기존 사적 대화에 임의로 업무 채널을 덧씌우지 않았다. 추가 설계는 thread_id, channel(personal/company), contact, message_id, 선택 효과 ID를 명시하고 기존 개인 thread_id를 유지하는 방식이다. 실제 회사 대사와 프로필 내용은 승인된 설정에서 따로 작성해야 한다. 실시간 AI 채팅은 추가하지 않는다.

저장소 목록에서 캐릭터용 moc3/model3/motion3/cmo3 모델을 확인하지 못했다. Windows/renpy/gl2의 Live2D 엔진 코드가 있는 것은 캐릭터 리깅 완료를 뜻하지 않는다. P1~P5/레이어 계획 문서와 실제 완성 파츠도 구분한다.

기본/특별 의상은 기존 R15 home/cosplay 등의 선택 기록과 슬롯을 보존한다. 사용자 로컬 AI가 제공할 확정 외형 PNG/레이어/의상에 맞춰 기존 정적 표시를 먼저 연결하고, 검증된 모델이 들어온 뒤에만 Live2D 표시를 덧붙인다. 이번에는 그림·속옷·신체·의상·리깅을 생성하거나 수정하지 않았다.

## 9. 검증 결과와 한계

실행한 것:
- LF로 정리한 고정 커밋의 텍스트 사본에서 `git apply --check`를 통과했다. 실제 전체 Git 체크아웃/Windows 줄바꿈 설정에서의 적용·스테이징은 별도 확인 대상이다.
- 신규 순수 Python 모델 및 정적 연결 검사 38개 통과. 그 안에 A/B/C/D 수치 조합484개가 포함된다.
- 상/하한·증감·인물 격리·중복 방지·미발견 이벤트·교제/현재 동의/필수 플래그 부족·누락 이미지·실제 경로·표정 대체·회상 중 해금 방지·기존 결말 ID를 검사했다.
- 새 모델의 JSON 왕복/과거 상태 복원은 테스트했다. 이는 Ren’Py 세이브·로드 시험과 다르다.
- 원본 대본의 기록 호출을 제거하면 대사/선택/분기가 원본과 일치하는지 정적 비교했다. 예외는 명시한 호감도 하한과 시험 파일 배포 제외 규칙이다.
- 읽은 텍스트에서 GitHub/AWS 키·개인키 헤더 패턴을 값 출력 없이 검사했다. 해당 패턴 일치는 없었다.

하지 못한 것:
- Ren’Py 패키지/SDK가 현재 환경에 없어 lint·게임 시작·실제 저장/로드·롤백·272지점 재진입·Replay 종료·화면 오버플로·오디오를 실행하지 않았다.
- 기존 Windows EXE/DLL/rpyc, 개인 save/persistent, 전체 Git 이력, GitHub/Google 계정의 권한과 세션은 읽거나 검사하지 않았다.
- 실제 독자의 재미·읽기 시간·상업용 밸런스·Steam 연동·배포 체크리스트를 통과했다고 하지 않는다.
- 이미지가 없는데 가짜 CG 감상 통과를 만들어 검사하지 않았다.
- Git 브랜치/커밋 생성과 원격 푸시·병합은 하지 못했거나 하지 않았다.
